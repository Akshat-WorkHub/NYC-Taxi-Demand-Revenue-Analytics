# Project Context

## Purpose and portfolio use

Analyze NYC Yellow and Green taxi demand, revenue, mobility, geography, and payment behavior for an interactive Power BI portfolio project. The README describes the source as official NYC TLC trip records and the intended use as a demonstration of data preparation, analysis, modeling, and dashboard design for analytics roles. Business questions include when demand peaks, how taxi types differ, where trips occur, how revenue changes, and how distance, duration, and payment behavior vary.

## Data and workflow

- The README identifies NYC TLC monthly Parquet trip records as the source, covering January 2024 through July 2026. Raw files are not intended for Git.
- `scripts/aggregate_for_powerbi.py` reads cleaned Parquet files under `data/processed/{yellow,green}`, processes batches of 100,000, filters to 2024-01-01 through 2026-07-31, and writes five aggregate Parquet outputs under `data/powerbi`.
- Those aggregates are `fact_daily`, `fact_hourly`, `fact_location_daily`, `fact_payment_daily`, and `fact_route`. The report model consumes aggregates; do not import full raw trip detail for report design.
- The README also describes MySQL analysis, but the repository files inspected here do not establish its current configuration or whether credentials/data are present. Verify before relying on MySQL workflow details.
- `requirements.txt` lists pandas, pyarrow, requests, beautifulsoup4, numpy, scikit-learn, and tqdm.

## Power BI model

The PBIP is `NYC_Taxi_Demand_Revenue_Analytics.pbip`. Its model definitions are in `NYC_Taxi_Demand_Revenue_Analytics.SemanticModel/definition/`; report definitions are in `NYC_Taxi_Demand_Revenue_Analytics.Report/definition/`.

Tables declared in `model.tmdl`: `Fact_Daily`, `Fact_Hourly`, `Fact_Location_Daily`, `Fact_Payment_Daily`, `Fact_Route`, `Dim_Date`, `Dim_Taxi`, `Dim_Payment`, `Dim_Pickup_Location`, `Dim_Dropoff_Location`, and `NYC_Taxi_Zones`.

Four measures are confirmed in `Fact_Daily.tmdl`: `[Total Trips]`, `[Total Revenue]`, `[Total Fare]`, and `[Total Tips]`. Useful verified columns include:

- `Dim_Date`: `Date`, `Year`, `Month Name`, `Year Month`, `Day Name`, `Week Number`, `Is Weekend`.
- `Fact_Daily`: `pickup_date`, `taxi_type`, `total_trips`, `total_revenue`, `total_fare`, `total_tips`, `total_distance`, `total_duration_minutes`, passenger count fields.
- `Fact_Hourly`: `pickup_date`, `pickup_hour`, `taxi_type`, `total_trips`.
- Location facts/dimensions: `pickup_location_id`, `dropoff_location_id`, `Zone`, `Borough`; `Fact_Route` contains pickup and dropoff IDs and trip aggregates.
- Payment: `Fact_Payment_Daily` contains `payment_type`, `taxi_type`, and aggregates; `Dim_Payment` contains `Payment Method`.

Relationships in `relationships.tmdl` connect each daily/hourly/location/payment fact to `Dim_Date`; daily/hourly/location/payment/route facts to `Dim_Taxi`; payment fact to `Dim_Payment`; route and location daily facts to `Dim_Pickup_Location`; and route to `Dim_Dropoff_Location`. No relationship to `NYC_Taxi_Zones` is declared. Verify exact bindings and relationship behavior in TMDL before using them; do not infer extra relationships.

## Known limitations and validation

- TMDL partitions contain machine-specific absolute paths into this repository's `data/powerbi` and to root `NYC_Taxi_Zones.csv`; refresh/open behavior on another machine may require path configuration. Do not refresh as part of report design without explicit scope.
- The aggregation script sums `total_distance` over all rows while `distance_count` counts only nonnegative distances. Its passenger total is not restricted to the rows counted in `passenger_count_records`. The report therefore does not calculate weighted average distance or passenger count: distance is labeled as a net recorded total, and passenger count as the reported total.
- `Average Trip Duration (Minutes)` uses `total_duration_minutes / duration_count`. The aggregation script documents that negative durations are removed during cleaning; the generated Parquet values were not audited here. `Average Payment Tip` uses the matching tip sum and non-null tip count.
- Geographic route results cover all available dates because `Fact_Route` has no date relationship. The route table uses distinct PBIR native/display names `Pickup Zone` and `Dropoff Zone`. `NYC_Taxi_Zones` remains unused. Four active pickup IDs have no mapped zone/borough row; the active-ID KPI includes them, while borough and Manhattan analysis cannot assign those IDs to a named area.
